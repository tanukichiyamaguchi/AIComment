# じっせん君コメントシステム

歯科医院の実践事例PDF（数百件）を読み取り、Claude Sonnet 4.6 API で **医院名・氏名・実践事例タイトル** を本文から自動抽出し、コンサルタント風コメントを生成、コメントページを末尾に追加した新PDFを **Google Drive に「<医院番号>_<医院名>/個人名/」階層** で保存し、**スプレッドシート「出力一覧」** に履歴を記録するシステム。

事前のスプレッドシート入力は不要。Drive にPDFを置けば自動で処理されます。

## セットアップ

### 1. Python環境

```bash
pip install -r requirements.txt
```

### 2. 環境変数 / Secrets

|--------|------|------|
| `ANTHROPIC_API_KEY` | Claude APIキー | ✅ |
| `GOOGLE_CREDENTIALS_JSON` | GCPサービスアカウントJSON（Sheets書き込み用、ローカル/Colab実行時） | ✅（GitHub Actions 以外） |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | Workload Identity 連携プロバイダ（GitHub Actions の Sheets認証用） | ✅（GitHub Actions） |
| `GCP_SERVICE_ACCOUNT` | Workload Identity 連携で借用するサービスアカウントのメールアドレス | ✅（GitHub Actions） |

| `DRIVE_FOLDER_ID` | 入力PDFが格納されたGoogle DriveフォルダID（`jissen_default` プロファイル用） | ✅（既定プロファイル使用時） |

#### `GOOGLE_OAUTH_TOKEN_JSON` がなぜ必要か

サービスアカウントは Google Drive の **マイドライブ** 配下に新規ファイルをアップロードできません（`storageQuotaExceeded` エラー）。これは Google の仕様で、サービスアカウントには 0GB の容量しか割り当てられていないためです。

回避策は次の2つ：

1. **OAuthユーザートークンを使う**（本実装の方針） — Driveアップロード時はユーザー認可で実行し、ファイル所有者をユーザー本人にする。本人の Drive 容量（個人/Workspace）を消費する
2. 共有ドライブを使う（Google Workspace Business Standard 以上が必要）

#### `GOOGLE_OAUTH_TOKEN_JSON` の取得手順

OAuthユーザートークンは下記スコープを含む必要があります：

```
https://www.googleapis.com/auth/drive
https://www.googleapis.com/auth/spreadsheets
https://www.googleapis.com/auth/gmail.compose
```

トークンJSON生成手順（**Codespacesで完結**、ローカルPCは不要）：

1. GCPコンソール → APIとサービス → OAuth同意画面：User Type を **External**、テストユーザーに自分のGmailを追加、スコープに上記3つを追加
2. GCPコンソール → APIとサービス → 認証情報 → 「OAuth 2.0 クライアント ID」を作成（種類：**デスクトップアプリ**）
3. JSONをダウンロード → Codespaces の `AIComment/` 直下にドラッグ&ドロップでアップロード → ファイル名を **`client_secret.json`** にリネーム（`.gitignore` で保護済み、誤コミットされません）
4. Codespacesターミナルで実行:
   ```bash
   pip install -r requirements.txt
   python scripts/generate_oauth_token.py
   ```
5. スクリプトが表示する認証URLをブラウザで開き、Google認証 → 3スコープすべてを許可
6. 認証後、ブラウザは「このサイトにアクセスできません」エラーになる（**正常**）。アドレスバーのURLを全部コピー → スクリプトに貼り付けて Enter
7. 生成された `token.json` の内容（`refresh_token` を含む）を `GOOGLE_OAUTH_TOKEN_JSON` Secret に貼り付ける

> ⚠️ `client_secret.json` は **絶対に Git コミットしない**こと。Public リポジトリの場合は瞬時に漏洩します。`.gitignore` で保護されていますが、念のため `git status` でステージされていないことを確認してください。

### 4. スプレッドシート「出力一覧」シート

プロファイル定義の `output_sheet_name`（既定は `出力一覧`）に該当するシートが存在しなければ初回実行時に自動作成されます。1ファイル1行で記録：

| 列 | ヘッダー | 内容 |
|----|---------|------|
| A | 管理番号 | PDF のファイル名先頭のコード（例: `001-01-0`）。`NNN-NN-N` 形式（先頭セグメント 3〜5桁 - 数字2 - 数字1）。CDC 医院見学レポートは 3 番目のセグメントが無い `NNN-NN`（例: `001-01`）も可。先頭セグメントが医院番号。いずれの形式でも始まらない場合は空欄 |
| B | 医院名 | AIがPDFから自動抽出 |
| C | 個人名 | AIがPDFから自動抽出 |
| D | 実践事例名 | AIがPDFから自動抽出 |
| E | Drive URL | 出力PDFの閲覧URL |
| F | 処理日時 | システムが書き込み |

> 事前の入力（医院名や氏名のリスト）は **不要**。AIがPDF本文から判別できなかった場合は `unknown_clinic` / `unknown_person` として処理を続行します。

> 添付資料 PDF（後述の §4-2）も同じ出力一覧シートに 1 行記録されます。その行の **実践事例名（D 列）は `【添付資料】` で始まる**ため、メイン実践事例の行と種別が一目で区別できます。

#### 増分処理（重複検知）

入力フォルダに PDF を少しずつ追加して **同じワークフローを複数回実行** する運用に対応しています。再実行時、システムは出力一覧シートの A列（管理番号）を読み取り、**既に記録済みの管理番号を持つ PDF をスキップ** します。これにより出力先（Drive / シート）に重複が増殖しません。

- **判定キーは管理番号**（ファイル名先頭の `NNN-NN-N` または `NNN-NN`）。再実行をまたいで安定したキーが必要なため。
- 管理番号は 2 形式に対応します: 実践事例 PDF の `NNN-NN-N`（3 セグメント）と、**CDC 医院見学レポートの `NNN-NN`（2 セグメント、3 番目の番号が無い）**。どちらも先頭セグメント（3〜5 桁）が医院番号です。
- 重複判定は **PDF の download / Claude API 呼び出しの前** に行われるため、処理済み PDF にはコストが発生しません。
- 管理番号を持たない PDF（先頭が `NNN-NN-N` / `NNN-NN` 形式でない）は重複検知が原理的にできないため、毎回再処理せず **警告ログを出してスキップ** します（`管理番号なしスキップ`）。
- `test_count` は「重複・管理番号なしを除いた **新規 PDF**」に対して適用されます（例: `test_count=5` なら新規 5 件まで）。
- 重複判定は **出力シート単位**（プロファイル / `target_folder` ごとに独立）です。
- 処理済みの PDF を **あえて再処理したい** 場合は、出力一覧シートの該当行を手動で削除してください。その管理番号は「未処理」扱いに戻り、次回実行で再処理されます（既存の重複行の自動削除は行いません）。

完了ログには内訳が出力されます（例: `成功: X件（メイン + 添付資料）, テキスト抽出失敗: X件, 管理番号なしスキップ: X件, 処理済みスキップ: X件, 添付資料メイン不在スキップ: X件, エラー: X件`）。

### 4-2. 添付資料ファイル（AI 処理せず出力先へコピー）

ファイル名に **`【添付資料】`**（全角の隅付き括弧込み）を含む PDF は、実践事例の **補足資料** として扱われます。これらは:

- **AI 処理を一切しません**（テキスト抽出 / Claude API 呼び出し / コメントページ生成 / PDF 結合をしない）
- メインの実践事例 PDF と **同じ管理番号**（`NNN-NN-N` 形式、ファイル名先頭）を持ちます
- 同じ管理番号のメイン実践事例 PDF と **同じ `<医院名>/<個人名>/` フォルダ**へ、**元のファイル名のまま**コピーされます
- 出力一覧シートにも記録されます（実践事例名 列が `【添付資料】...` で始まる）

運用上の注意:

- **メインの実践事例 PDF と添付資料は、同じ入力フォルダ・同じ実行に入れてください。** 添付資料は「同じ管理番号のメイン実践事例 PDF がその実行で処理されたこと」を前提に出力先（医院名 / 個人名）を決めます。対応するメインが同じ実行に無い添付資料は、警告ログを出してスキップされます（`添付資料メイン不在スキップ`）。
- 添付資料も増分処理（重複検知）の対象です。前回実行で出力一覧シートに記録済みの管理番号を持つ添付資料は、再実行時にスキップされます。
- Batch モードでも添付資料は Claude API（Batch API）に投げられず、メイン PDF のバッチ処理完了後（Step 4）にコピーされます（API 料金は発生しません）。

例（管理番号 `001-01-0` のメイン + 添付資料）:

```
入力フォルダ/
├── 001-01-0実践事例タイトル.pdf            ← メイン（AI 処理する）
└── 001-01-0【添付資料】補足データ.pdf       ← 添付資料（AI 処理しない・コピーのみ）

出力/
└── 001_三浦歯科医院/
    └── 白川 蓮/
        ├── 三浦歯科医院＿白川 蓮＿AI活用インプラント新患獲得.pdf  ← メイン（元PDF＋コメントページ）
        └── 001-01-0【添付資料】補足データ.pdf                      ← 添付資料（元ファイルのまま）
```

### 4-3. 医院フォルダURLシート（医院ごとのフォルダ URL 一覧）

出力一覧シートとは別に、**医院ごとの Drive フォルダ URL** を記録する専用シートが自動作成されます。

- シート名は **`<出力シート名>_医院`**（例: 出力シートが `26年実践事例1回目` なら `26年実践事例1回目_医院`、既定プロファイルなら `出力一覧_医院`）。該当シートが無ければ初回実行時に自動作成されます。
- 列は **3 列**:

  | 列 | ヘッダー | 内容 |
  |----|---------|------|
  | A | 医院番号 | 管理番号 `NNN-NN-N` の先頭セグメント（3〜5桁、例 `001`） |
  | B | 医院名 | 参加者マスターシート（§4-4）から引いた標準表記。未登録時は AI 抽出値で代用 |
  | C | 医院フォルダURL | 医院フォルダ（`<医院番号>_<医院名>/`）の Drive URL |

- **同じ医院は 1 行のみ**記録されます。1 つの医院に複数の実践事例 PDF があっても医院フォルダ URL シートには重複追加されません（医院番号 A 列をキーに重複判定）。再実行時も、既に記録済みの医院番号はスキップされます。
- **チーム事例（§4-5）の配布先メンバーの医院も記録されます**。チーム配布でメンバーの医院フォルダが作成・利用された場合、その医院フォルダ URL も本シートに 1 行記録されます（提出者の医院だけでなく、チーム全員分の医院フォルダ URL がこのシートで一覧できます）。

### 4-4. 参加者マスターシート（医院名標準化 + Gmail 下書き作成用ルックアップ表）

実践事例 PDF の処理時に、専用シート（参加者マスタータブ）から (1) 医院名の標準表記、(2) Gmail 下書きの送信先メールアドレス、の 2 つを引きます。同じシートを 2 用途で兼ねることで、ユーザーが運用するシートを 1 つに統一しています。

- **target_folder モード**（推奨・後述 §「フォルダ自動検出モード」）: タブ名は **`参加者マスター(<セミナー名>)`** をセミナーごとに使います。入力フォルダ名が**セミナー名を含む**全フォルダで同じタブを参照します（例: タブ `参加者マスター(新人育成塾)` を作っておけば、フォルダ `新人育成塾` / `新人育成塾_2026_Q1` / `2026_新人育成塾_実践事例` のいずれからの実行でも同じタブが参照される）。複数のセミナー名が含まれる場合は**最長一致**を採用（より具体的なセミナー名を優先）。マッチするタブが**不在 or 0 件のときは PDF 処理に入る前に HARD FAIL で即停止**します（下書きが全件宛先空・医院名フォルダが AI 抽出値で作成される事故を未然に防ぐ）。Batch モードでは Anthropic API 投入前に Step 1 でガードします。
- **profile モード**（旧式・後方互換）: 既定タブ名は **`参加者マスター`**（共有 1 枚で使い回し）。プロファイル YAML の `master_sheet_name` で上書き可能。タブが空でも HARD FAIL せず WARNING + 続行（既存運用維持）。
- シートが無ければ初回実行時に **自動作成され、ヘッダー行だけ書き込まれた空シート**が用意されます。target_folder モードではこの空タブを検知して HARD FAIL で停止するため、運用者は必ず参加者行を投入してから再実行してください。
- 列は **6 列**（1 行 per 個人。F 列は任意）:

  | 列 | ヘッダー | 内容 |
  |----|---------|------|
  | A | 管理番号 | 実践事例 PDF のファイル名先頭の `NNN-NN-N` 形式（例 `101-01`、桁数は 3〜5 - 2 - 1） |
  | B | 医院名 | 標準表記の医院名。同一医院の複数行（例 `101-01`/`101-02`）は同じ値を重複記入してよい。「開業準備中」等の固定文字列もそのまま標準名として扱う |
  | C | 参加者名 | Gmail 下書き宛先の個人特定（AI 抽出名との突合キー）と、チーム事例配布時の個人フォルダ名に使う |
  | D | 申し込み会場 | 参照用（システムは見ない） |
  | E | メールアドレス | Gmail 下書きの TO に使う |
  | F | 所属チーム | **任意**。チーム事例（§4-5）の配布先解決に使う。空なら配布なし。既存の 5 列タブはこの列が無いままで従来どおり動作 |

- 形式不正のメール（`@` がない等）はその列だけ空扱い + 警告ログで通知します（行自体は残り、医院名 lookup には使えます）。

#### 医院名標準化（フォルダ命名・各種シート列）

PDF ファイル名から **医院番号**（管理番号 `NNN-NN-N` の先頭セグメント、例 `101-01-0` → `101`）を取り出し、参加者マスターシートで `管理番号` の **prefix 一致**（`101-` で始まる行）を検索します:

- **一致行あり** → その行の B 列「医院名」を以後すべての医院名用途で使用（医院フォルダ命名・出力一覧シートの医院名列・医院フォルダURLシート・PDF 内コメントヘッダー）
- **一致行なし、または医院名空** → AI が PDF から抽出した医院名で代用（**警告ログ + 処理続行**）

「開業準備中」のように B 列に固定文字列を書いておけば、その医院番号の PDF はすべて `<医院番号>_開業準備中/...` フォルダにまとまります。

#### Gmail 下書きの TO ルックアップ

PDF の管理番号（`101-01` 等の完全な文字列）で参加者マスターの A 列を **完全一致** 検索します:

- **一致行あり + メール非空** → TO = その行の E 列メールアドレス、CC なし
- **一致行なし、または一致行のメール空** → **下書き作成をスキップ + 警告ログ**（PDF 処理は続行・fail-soft）

メール未登録時のスキップは PDF 処理自体には影響しません（PDF アップロード・出力一覧シート追記は通常通り完了）。下書きを後から作りたい場合は、参加者マスターに行を追加 → 出力一覧シートの該当行を削除 → 再実行、の手順でその管理番号が「未処理」扱いに戻り、再処理と一緒に下書きも再作成されます。

#### 下書きの件名・本文

- 件名: `【実践事例】じっせん君コメント ─ <個人名>様`
- 本文: 定型文（`gmail_client.BODY_TEMPLATE` を参照）

メイン PDF と添付資料 PDF（後述 §4-2）の **両方** で同じテンプレートの下書きが作成されます（メールごとに件名を変えると受信側が混乱するため）。

#### 下書きの重複作成防止

下書きは PDF 処理の **副作用** です。重複作成防止は **管理番号デデュープ**（前述 §4「増分処理」）に従います: 出力一覧シートに既存の管理番号を持つ PDF はスキップされるため、その下書きも再作成されません。下書き側に独自の重複チェックはありません（lessons.md P-020）。

#### プロファイル YAML での指定例

```yaml
# profiles/jissen_2024_q1.yaml
output_sheet_name: "実践事例_2024Q1_出力一覧"
master_sheet_name: "実践事例_2024Q1_参加者マスター"   # ← セミナーごとに専用シート
```

`master_sheet_name` を省略するとグローバル既定値 `参加者マスター` にフォールバックします。新しいセミナーを追加するときは、上の例のような YAML を 1 つ作り、対応する Drive フォルダの Secret を 2 つ追加するだけです。

### 4-5. チーム事例の全員配布（所属チーム F 列）

ファイル名に **`チーム実践_`** または **`チームMTG_`** を含む PDF（例:
`001-01-0【α】チーム実践_接遇改善.pdf`）は「チーム事例」として扱われ、コメント入り PDF が
**報告者と同じチームの全メンバーのフォルダ**にコピーされます。

- 配布先は参加者マスターで解決します: ファイル名冒頭の管理番号 → マスター A 列で報告者の
  行を特定 → その行の **F 列「所属チーム」** と同じ値を持つ全行が配布先（チーム名の比較は
  全角/半角・空白の揺れを吸収）
- 各メンバーの `<医院番号>_<医院名>/<参加者名>/` へ、報告者分と**同じファイル名**で保存されます
- **出力一覧シートには報告者 1 行 + 配布した各メンバー 1 行ずつ**が記録されます。メンバー行は
  報告者と同じ管理番号を使い、実践事例名の先頭に `【チーム配布】` を付けて報告者本人の行と
  区別します（添付資料の `【添付資料】` マーカーと同じ考え方）。医院名・個人名・Drive URL は
  各メンバー自身のコピーの値です
- **医院フォルダURLシート（§4-3）には配布先メンバーの医院も記録されます**。チーム配布で
  作成・利用されたメンバーの医院フォルダ URL も `<出力シート名>_医院` シートに 1 医院 1 行で
  追加されるため、チーム全員分の医院フォルダ URL を一覧できます
- **Gmail 下書きは従来どおり報告者のみ**（メンバーには作成しません）
- 報告者がマスター未登録、または F 列が空の場合は **警告ログを出して報告者のフォルダのみ**に
  保存します（従来動作へのフォールバック）
- 配布はシート記録より**前**に行われるため、途中で失敗した場合はその PDF 全体がエラー扱いに
  なり、再実行で配布からやり直されます（アップロードは同名スキップで冪等 = 重複しません）

### 5. Drive 出力構造

医院フォルダ名は **`<医院番号>_<医院名>`** 形式（区切りは半角アンダースコア `_`）。医院番号は管理番号 `NNN-NN-N` の先頭セグメント（最初のハイフンより前、3〜5 桁）です。例: 管理番号 `001-01-0` → 医院番号 `001` → フォルダ名 `001_三浦歯科医院`。

```
<DRIVE_OUTPUT_FOLDER_ID>/
├── 001_三浦歯科医院/
│   └── 白川 蓮/
│       ├── 三浦歯科医院＿白川 蓮＿AI活用インプラント新患獲得.pdf  ← 元PDF＋コメントページ
│       └── 三浦歯科医院＿白川 蓮＿自費率向上の取り組み.pdf
├── 002_山本歯科医院/
│   └── 田中 太郎/
│       └── 山本歯科医院＿田中 太郎＿夏祭りイベント開催.pdf
└── unknown_clinic/         ← 医院名抽出失敗時のフォールバック
    └── unknown_person/
        └── unknown_clinic＿unknown_person＿名称不明事例.pdf
```

- 医院番号（フォルダ名の接頭辞）は管理番号から機械抽出した安定値です。医院名は参加者マスターシート（§4-4）から引いた標準表記。未登録の場合のみ AI 抽出値で代用します（警告ログ付き）。
- **医院フォルダは医院番号で識別されます。** AI が同じ医院でも医院名を違う表記で抽出した場合（例: `三浦歯科医院` / `三浦歯科` / `医療法人三浦歯科`）、同じ医院番号のフォルダが既にあれば **そのフォルダを再利用** します。AI 抽出値では医院名部分をリネームしませんが、**参加者マスターに登録された確定医院名のときは、既存フォルダ名もその確定名へリネームして揃えます**（フォルダ ID・URL は不変なので既存リンクは保持されます）。フォルダ識別子部分（`<医院番号>_`）のみで前方一致判定するため、語そのものが違う医院名表記揺れでも重複フォルダが作られません。
- 管理番号が `NNN-NN-N` 形式で始まらない PDF は医院番号を持てないため、医院番号なし（医院名のみ）のフォルダ名にフォールバックし、その場合のみ従来通り医院名の正規化マッチング（半角/全角・空白の揺れ吸収）でフォルダを照合します。
- **既存の番号なしフォルダ（`三浦歯科医院/` など）はこの変更後も孤立したまま残ります。** 新しい出力は `001_三浦歯科医院/` のような番号付きフォルダへ入るため、旧フォルダと別物として扱われます。自動移行は行いません（必要なら手動で統合してください）。
- **同じ医院番号で複数フォルダが既存する場合**（本仕様導入前にできた重複）は、フォルダ ID 昇順で決定論的に 1 つを再利用し、警告ログに重複 ID 一覧を出します（自動統合は行いません＝破壊的変更を避けるため。手動統合を推奨。なお再利用したフォルダは、確定医院名が分かれば上記のとおりリネームされます）。

PDF のファイル名は ``<医院名>＿<個人名>＿<実践事例タイトル>.pdf`` 形式（区切りは全角アンダースコア ``＿``）。AI が抽出した値から特殊文字を除いて生成。

## プロファイル

### なぜ必要か

「ドキュメントタイプ × 提出期間」の組み合わせごとに **入力フォルダ / 出力フォルダ / 出力一覧シート** を切り替えるための仕組み。同一ワークフローを 1 本だけ保ったまま、四半期ごとの実践事例を別フォルダ・別シートに整理して処理できる。

```
[現状] 1 ワークフロー → 固定の {入力/出力/シート/プロンプト} を直接参照
[新規] 1 ワークフロー → --profile 引数 → プロファイル定義 → 各種設定を解決
```

### 利用可能なプロファイル

`profiles/*.yaml` に定義。コマンドラインからは `python -c "from src.profile import list_available_profiles; print(list_available_profiles())"` で一覧取得可能。

| プロファイル名 | 入力 Secret | 出力 Secret | 出力シート |
|---------------|------------|------------|-----------|
| `jissen_default` | `DRIVE_FOLDER_ID` | `DRIVE_OUTPUT_FOLDER_ID` | `出力一覧` |
| `jissen_2024_q1` | `DRIVE_FOLDER_JISSEN_2024_Q1` | `DRIVE_OUTPUT_JISSEN_2024_Q1` | `実践事例_2024Q1_出力一覧` |
| `jissen_2024_q2` | `DRIVE_FOLDER_JISSEN_2024_Q2` | `DRIVE_OUTPUT_JISSEN_2024_Q2` | `実践事例_2024Q2_出力一覧` |
| `jissen_2024_q3` | `DRIVE_FOLDER_JISSEN_2024_Q3` | `DRIVE_OUTPUT_JISSEN_2024_Q3` | `実践事例_2024Q3_出力一覧` |
| `jissen_2024_q4` | `DRIVE_FOLDER_JISSEN_2024_Q4` | `DRIVE_OUTPUT_JISSEN_2024_Q4` | `実践事例_2024Q4_出力一覧` |

管理番号はプロファイルに依らず、実践事例 PDF のファイル名先頭の `NNN-NN-N` 形式コードから抽出する（§4 参照）。

`jissen_default` は **既存挙動を完全維持する後方互換プロファイル**。`--profile` 引数を省略した場合の既定値でもあり、過去の Secret / シートがそのまま動く。

### 新しいプロファイルを追加する手順

1. `profiles/<新プロファイル名>.yaml` を作成。schema は下記を参照
2. GitHub Secrets に `input_folder_id_secret` / `output_folder_id_secret` で指定したキー名で Drive フォルダ ID を登録
3. `.github/workflows/generate_comments.yml` の `env:` セクションに `<KEY>: ${{ secrets.<KEY> }}` を追記
4. （オプション）Google フォームのプルダウン選択肢と Apps Script の `ALLOWED_PROFILES` 配列に新プロファイル名を追加

> **新セミナーを 1 つ追加するたびに上記 4 ステップが必要になる** ため、増える数が読めない用途では下記「フォルダ自動検出モード」のほうが運用負荷が低い。

## フォルダ自動検出モード

### なぜ便利か

セミナー種類 × 回数 × 提出物種類が今後増える用途に向けた **Convention over Configuration** 設計。**Drive にフォルダを作るだけで全自動で処理対象になる** ため、新しい種別を追加するたびに Secret / YAML / Apps Script を編集する必要がない。

```
[従来] 新セミナー → profiles/*.yaml + GitHub Secret × 2 + workflow YAML 編集 + Apps Script 編集
[新規] 新セミナー → Drive にサブフォルダ作成 + PDF アップロードのみ
```

| 観点 | プロファイルモード | フォルダ自動検出モード |
|------|------------------|-------------------|
| 新セミナー追加時のコード変更 | あり（YAML + workflow YAML） | **なし** |
| 新セミナー追加時の Secret 追加 | あり（入力 ID + 出力 ID の 2 つ） | **なし** |
| 命名規約の自由度 | YAML で固定 | Drive フォルダ名に従う |
| 既存挙動との関係 | 完全維持（後方互換） | 追加機能（profile と排他で選択） |

### セットアップ手順（一度だけ）

1. Drive で「入力サブフォルダの親フォルダ」を 1 つ作成（例: `アプコメ入力ROOT`）→ フォルダ ID を控える
2. Drive で「出力サブフォルダの親フォルダ」を 1 つ作成（例: `アプコメ出力ROOT`）→ フォルダ ID を控える
3. GitHub Secrets に下記 2 つを追加（既存 Secret は触らない）:
   | Secret 名 | 値 |
   |-----------|-----|
   | `DRIVE_INPUT_ROOT` | 手順 1 のフォルダ ID |
   | `DRIVE_OUTPUT_ROOT` | 手順 2 のフォルダ ID |
4. `SPREADSHEET_ID` は既存と同じものを引き続き使う（タブが自動で作成される）

### 使い方（毎回）

1. Drive で `DRIVE_INPUT_ROOT` 配下にサブフォルダを作成（命名自由、例: `2024_Q1_実践事例` / `2025_新人研修_中間レポート`）
2. そのフォルダに対象 PDF をアップロード
3. GitHub Actions ワークフローを起動し、`target_folder` 入力欄にフォルダ名を入れる（例: `target_folder: 2024_Q1_実践事例`）
4. `profile` 入力欄は無視される（target_folder が優先）

### システムが自動でやること

1. `DRIVE_INPUT_ROOT` 配下から `target_folder` 名のフォルダを検索（半角/全角・空白の有無の表記揺れは自動吸収）
2. `DRIVE_OUTPUT_ROOT` 配下に同名フォルダを作成（既存ならスキップ）
3. `SPREADSHEET_ID` に同名タブを作成（既存ならスキップ）
4. **参加者マスタータブの存在チェック**: `参加者マスター(<フォルダ名>)` タブが不在 / 0 件なら HARD FAIL（投入前に停止し、出力一覧シートに「中止」マーカーを 1 行追記。Anthropic 料金の無駄を防ぐ）
5. 既存処理パイプライン（PDF 取得 → Claude API → コメント PDF 生成 → 結合 → Drive 保存 → Sheets 追記）を実行

### 命名規約と派生ルール

- **フォルダ名 = 出力タブ名**（例: `新人育成塾` → 出力タブ `新人育成塾`）
- **参加者マスタータブ名 = `参加者マスター(<セミナー名>)`**（例: タブ `参加者マスター(新人育成塾)`）。セミナーごとに独立した参加者管理。**フォルダ名がセミナー名を含むなら同じタブを参照**するため、年度・期ごとに `新人育成塾_2026_Q1` のようにフォルダを分けても、マスタータブは 1 枚（`参加者マスター(新人育成塾)`）で運用可能。複数のセミナー名が含まれる場合は最長一致を優先
- フォルダ名の sanitize は最小限。Drive で許される文字（半角/全角の日本語、英数字、`_` `-` 等）は基本そのまま使われる
- 表記揺れマッチング: 「`医療法人 かがやき`」と「`医療法人かがやき`」のような半角/全角空白の有無や全角/半角英数字の差異は **同一フォルダ** と見なし、重複作成を防ぐ（lessons.md P-009 と同じ方針）
- 管理番号は **実践事例 PDF のファイル名先頭の `NNN-NN-N` 形式コードから抽出**する（target_folder モードでもプロファイルモードと同じ）。ファイル名がこの形式で始まらない場合は空欄になる（§4 参照）

### 候補名を確認する

「いま `DRIVE_INPUT_ROOT` 配下に何のサブフォルダがあるか」を確認したい場合は `target_folder` に `__list__` を入力してワークフローを実行する。Actions のログに候補一覧が表示される（PDF 処理はスキップ）。

### コマンドライン

```bash
# フォルダ自動検出モード（profile より優先）
python -m src.batch_main --target-folder "2024_Q1_実践事例" --test-count 5
python -m src.main --target-folder "2024_Q1_実践事例"

# 候補列挙のみ（処理しない）
python -m src.main --target-folder "__list__"
```

### profile モードとの選び方

| こんなときは | 選ぶモード |
|------------|----------|
| 既存の `jissen_default` / `jissen_2024_q1` 等で動いていて、変える必要がない | プロファイルモード（後方互換） |
| プロンプトテンプレートやドキュメント種別を切り替えたい | プロファイルモード（YAML で `prompt_template` 等を切り替え可能） |
| セミナー × 回数 × 提出物種類を頻繁に追加する | **フォルダ自動検出モード** |
| Secret/YAML を増やしたくない | **フォルダ自動検出モード** |

両モードは同時に存在でき、相互に干渉しない。同じワークフロー実行で `target_folder` が空なら profile が使われる。

YAML スキーマ（必須フィールド）：

```yaml
display_name: "（ログ表示用の人間可読名）"
document_type: jissen_practice_case          # 文書タイプ識別子
period: "2024_q1"                             # 期間識別子
input_folder_id_secret: DRIVE_FOLDER_XXX     # 環境変数名（解決はランタイム）
output_folder_id_secret: DRIVE_OUTPUT_XXX    # 環境変数名（解決はランタイム）
output_sheet_name: "実践事例_2024Q1_出力一覧" # 同一スプレッドシート内のシート名
prompt_template: jissen_practice_case        # コメント生成プロンプト識別子
```

> 管理番号は採番せず、実践事例 PDF のファイル名先頭の `NNN-NN-N` 形式コードから抽出するため、プロファイル/フォルダ自動検出のどちらでも prefix 設定は不要。

## 処理フロー（v2）

```
1. Drive入力フォルダから全PDFを取得
2. 入力PDFを「メイン実践事例」と「添付資料」に分類（ファイル名に「【添付資料】」を含むか）
3. 重複検知（増分処理）— download / Claude API 呼び出しの前に実施：
   a. 各PDFのファイル名から管理番号を抽出
   b. 管理番号なし → スキップ（警告ログ）
   c. 管理番号が出力一覧シートに既存 → スキップ（処理済み）
   d. それ以外 → 「処理対象（新規）」リストに追加
   e. test_count 指定時は新規メインPDFリストの先頭 N 件に絞る
4. 参加者マスターシートを 1 回読み込み（無ければ自動作成・空のヘッダーのみ）
5. 処理対象（新規）の各メインPDFについて：
   a. テキスト抽出
   b. Claude API（構造化出力）で 医院名・氏名・実践事例タイトル・コメントを一括取得
   c. 参加者マスターから医院番号で標準医院名を引く（未登録なら AI 抽出値で代用＋警告）
   d. コメントページPDFを生成（標準医院名を使用）
   e. 元PDF + コメントページを結合
   f. Drive `<出力root>/<医院番号>_<標準医院名>/<個人名>/<タイトル>.pdf` にアップロード
   g. 出力一覧シートに 1 行追記（医院名列は標準医院名）
   h. 参加者マスターから管理番号でメールアドレスを引き、Gmail 下書きを作成（CC なし）
      （メール未登録なら警告スキップ、例外時も処理を続行）
   i. 管理番号 → (医院番号, 標準医院名, 個人名) の対応表に登録
6. 添付資料パススルー（AI 処理なし）— メインPDF処理の完了後：
   a. 重複判定は「その添付資料自体が出力一覧シートに記録済みか」
      （`【添付資料】<元名>` マーカー）。メインの管理番号とは独立
   b. 添付資料の管理番号で 5-i の対応表を引く。対応するメインがこの実行に
      無ければ、参加者マスター（管理番号 → 医院名・参加者名）だけで出力先を
      解決する（メイン非依存フォールバック）。マスターにも無ければスキップ（警告ログ）
   c. 元PDFのバイト列をそのまま、メインと同じ <医院フォルダ>/<個人名>/ フォルダへ
      元ファイル名のままアップロード
   d. 出力一覧シートに「【添付資料】<元名>」で 1 行追記
   e. メイン経路と同じテンプレートで Gmail 下書きを作成
```

## 大量PDF運用の耐障害設計（止まらない・二重課金しない）

1000 件規模の本番運用を想定した保護機構。すべて自動で効く（設定不要）。

| 機構 | 内容 |
|------|------|
| **バッチ自動レジューム** | Batch 投入したバッチ ID をスプレッドシートの `_バッチ管理` タブに記録。GHA ジョブが途中で kill されても、次の `step=all` 実行が未回収バッチを検知して**再投入せず回収から再開**する（Anthropic への二重課金防止）。バッチ結果は 29 日保持 |
| **バッチのチャンク分割** | Batch API の上限（256MB/バッチ）に収まるようリクエストを自動分割して複数バッチで送信（数千件規模対応）。`batch_id.txt` は 1 行 1 ID、`--batch-id id1,id2` で複数回収可 |
| **新規 0 件の正常終了** | 増分運用で新規 PDF が無いとき、バッチ送信〜PDF 生成をスキップして正常終了（従来は赤ラン） |
| **ポーリングの自発タイムアウト** | step3 の結果待ちは既定 5h（`--poll-max-minutes`）。GHA の 6h 上限より先に明確なメッセージで終了し、次回実行の自動レジュームに引き継ぐ |
| **通常モードの時間バジェット** | `src.main` は既定 320 分でループを安全に打ち切り、処理済み分の Gmail 下書き・完了マーカーまで完走（`--max-runtime-minutes`、0=無制限）。未処理分は再実行の増分処理で継続 |
| **添付資料の恒久ロスト防止** | 添付資料の重複判定をマーカー（`【添付資料】<元名>`）ベースに変更 + 参加者マスター単独で出力先を解決するフォールバック。メイン処理後に添付だけ後から追加してもコピーされる |
| **Gmail 25MB 添付分割** | 1 通の添付合計が上限を超えるグループは自動で複数通に分割。単独超過ファイルは ERROR ログ + 添付から除外（Drive には保存済み） |
| **Gmail リトライ強化** | 下書き作成は指数バックオフ付き 5 試行 + googleapiclient 内蔵リトライの多層防御（ラン末尾一括作成のため失敗＝恒久ロストになるのを防ぐ） |
| **API クォータ保護** | Sheets 書き込み 28/分（2 ラン同時でも合算 56/分 < 上限 60/分）。シート ensure・Drive フォルダ解決はラン内キャッシュで read を数千回削減 |
| **巨大 PDF ガード** | 抽出テキストが 10 万文字を超える PDF は警告付きで切り詰め（コンテキスト超過による毎ラン再投入・再失敗ループを防止） |
| **認証エラーの即停止** | Google OAuth トークン失効（RefreshError）は per-item で握りつぶさず即停止（数百件の無駄な失敗ループを防ぐ） |

**GHA ジョブが途中で死んだら**: 何もしなくてよい。同じ `target_folder` で再実行（`step=all`）すれば、投入済みバッチは自動回収され、処理済み PDF は重複判定でスキップされ、続きから処理される。

### 処理速度（1000 件規模）

- **step1 の並列ダウンロード**: `STEP1_DOWNLOAD_WORKERS` 環境変数（本番 GHA は 4）。
  1000 件の逐次 15〜50 分を数分の一に短縮。**8 以下推奨**（Drive の per-user quota への配慮）。
  問題があれば `1` に戻すだけで完全に従来の逐次コードパスへ退避できる
- **Google API サービスのプロセス内キャッシュ**: `build()` + 認証 + トークンリフレッシュ
  （1 回数百 ms × 従来は呼び出しごと）を排除。step1/step4 の両方に効く
- **参加者マスターの 1 読み化**: batch の strict ガードと step4 の二重読みをメモ化で解消
- **メモリ目安**: 1000 件（平均テキスト 50KB）で約 115MB、5000 件（100KB）でも約 1.2GB
  （GHA ランナー 16GB 内）

## トラブルシューティング

| 問題 | 対処 |
|------|------|
| 出力一覧シートが空のまま | `DRIVE_OUTPUT_FOLDER_ID` がSecretsに設定されているか確認 |
| `Service Accounts do not have storage quota` 403エラー | `GOOGLE_OAUTH_TOKEN_JSON` が未設定。OAuthユーザートークンを設定すること（手順は「`GOOGLE_OAUTH_TOKEN_JSON` の取得手順」を参照） |
| Driveアップロードで `insufficient permissions` / `invalid_scope` エラー | OAuthトークンに `drive` スコープが含まれていない。スコープ3点を含めて再生成 |
| `unknown_clinic` / `unknown_person` フォルダに大量に入る | PDF本文からAIが判別できていない。PDFのフォーマットや書式を見直す |
| フォントダウンロード失敗 | 手動で `assets/` にNotoSansJP-Regular.ttf / Bold.ttfを配置 |
| PDFの文字が□ □ □ になる | フォントファイルが正しくダウンロードされているか確認 |
| Claude API 429エラー | 自動リトライあり。頻発する場合はBatchモード推奨 |
| GitHub Actions タイムアウト / ジョブが途中で死んだ | 同じ設定で再実行するだけでよい。投入済みバッチは `_バッチ管理` タブ経由で自動回収され（再投入・二重課金なし）、処理済み PDF は重複判定でスキップされる（§大量PDF運用の耐障害設計） |
| 同じPDFを再実行すると重複出力される | 管理番号（ファイル名先頭 `NNN-NN-N`）による重複検知が実装済み。再処理したい場合は出力一覧シートの該当行を削除して再実行 |
| バッチを投入したままランが死んで結果が取れない | スプレッドシートの `_バッチ管理` タブ（または GHA アーティファクトの `logs/batch_id.txt`）でバッチ ID を確認。`step=all` 再実行で自動回収、または `--step results --batch-id <id[,id2...]>` で手動回収（結果は 29 日保持） |
